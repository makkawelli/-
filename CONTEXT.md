## 1. Что это за проект

**Дипломный проект (ВКР).** Тема: **«Разработка информационной системы учёта
заявок на обслуживание клиентов»**.

Это веб-приложение на Django 5 + PostgreSQL 15, реализующее **систему тикетов**
для сервисной компании. Главная фишка / УТП проекта — **low-code-конструктор
пользовательских полей** (администратор может через админку добавить
произвольное поле в карточку заявки без правки кода и миграций — значения
хранятся в JSONB с GIN-индексом).

Проект **развивается итерационно по STEP-файлам** (`app/STEP_01.md` …
`app/STEP_05.md`). Каждый STEP — это законченный логический шаг: код,
инструкция по применению, чек-лист скриншотов для главы 3 ВКР.

## 4. Доменная модель (14 таблиц)

Файл — `app/core/models.py`. Соответствует
`artifacts/02_database/schema.sql` и `datalogical_schema.md`.

**Справочники:**
- `Role` (admin, manager, operator, executor, client)
- `Service` — услуги
- `Status` (`new`, `in_progress`, `on_hold`, `review`, `done`, `cancelled`)
- `Priority` — с полем `sla_hours` (норматив SLA в часах)
- `Team` — группы исполнителей

**Пользователи и контрагенты:**
- `Employee` — кастомная модель (наследует `AbstractUser`),
  + `full_name`, `position`, `role` (FK), `teams` (M2M)
- `Client` — клиент-контрагент

**Ядро:**
- `Request` — заявка. Номер вида `REQ-2026-000001`. Содержит JSONB-поле
  `custom_fields` для значений low-code-полей. На JSONB стоит GIN-индекс.

**Связанное:**
- `Comment` (с флагом `is_internal` — внутренние не показываются клиенту)
- `Attachment` — файлы (модель есть, UI пока минимальный)
- `StatusHistory` — пишется автоматом в `services.transition_request`
- `RoutingRule` — правила маршрутизации service → team
- `FieldDefinition` — **схема low-code-полей** (типы: text, textarea, number,
  date, select, checkbox; флаги required/active; порядок отображения)
- `AuditLog` — журнал значимых действий

## 5. RBAC (роли и доступ)

Реализован в `app/core/permissions.py`. 5 ролей:

| Роль | Видит заявки | Создаёт заявки | Редактирует карточку | Закрывает (done) | Отчёты | Клиенты |
|---|---|---|---|---|---|---|
| `admin` | все | да | да | да | да | редакт. |
| `manager` | все | да | да | **да** | **да** | редакт. |
| `operator` | все | да | да | нет | нет | редакт. |
| `executor` | только свои (assignee=user) | нет | нет | нет | нет | просмотр |
| `client` | — (через UI пока не работает) | — | — | — | — | — |

**Ключевые функции:**
`can_create_request`, `can_edit_request`, `can_view_request`,
`can_comment_request`, `can_view_reports`, `can_view_clients`,
`can_edit_client`, `visible_requests_qs(user)`, `can_transition`,
`allowed_transitions_for`.

## 6. Машина состояний (FSM) заявок

В `permissions.py`, словарь `ALLOWED_TRANSITIONS`:

```
new        → in_progress, cancelled
in_progress → on_hold, review, cancelled
on_hold    → in_progress, cancelled
review     → in_progress, done
done       → ∅ (терминальный)
cancelled  → ∅ (терминальный)
```

Дополнительные правила в `can_transition`:
- оператор не может переводить в `done` (только менеджер/админ);
- исполнитель может менять статус только своей заявки.

При переходе пишется запись в `StatusHistory` и `AuditLog`, отправляется
email клиенту (кроме перехода в `new` — это и есть создание).

## 7. Low-code конструктор полей (главное УТП)

**Как работает:**
1. Админ заходит в `/admin/core/fielddefinition/` и создаёт поле:
   `code='vehicle_vin'`, `label='VIN автомобиля'`, `field_type='text'`,
   `is_required=True`, `order_num=10`.
2. В `core/forms.py` метод `RequestForm.__init__` динамически добавляет
   соответствующие поля формы на основе `FieldDefinition.objects.filter(is_active=True)`.
3. На карточке заявки они показываются в блоке «Дополнительные сведения».
4. Значения сохраняются в `Request.custom_fields` (JSONB).
5. По JSONB есть GIN-индекс — фильтры работают быстро без миграций.

В демо-данных (`demo.py`) уже есть 3 поля:
`Серийный номер устройства` (text), `Срочность по мнению клиента` (select),
`Готов оплатить срочный выезд` (checkbox).

## 8. Отчёты (для менеджера/админа)

Файл — `app/core/reports.py`. 4 функции:

- `live_dashboard_metrics()` — открытых, просрочено, без исполнителя
- `report_by_period(date_from, date_to)` — динамика создания/закрытия по дням
- `report_executors()` — нагрузка исполнителей (Avg/Count/просрочка)
- `report_sla()` — соблюдение SLA по приоритетам (closed_at <= due_date)

UI: `/reports/` (индекс с метриками и 3 карточки-ссылки) →
`by-period`, `executors`, `sla`. На каждой странице есть кнопка
**«Скачать CSV»** (с BOM для корректной кириллицы в Excel).

На странице `by-period` — bar-chart на Chart.js.
На странице `sla` — цветовые бейджи: зелёный ≥95%, жёлтый ≥80%, красный <80%.

Доступ: `can_view_reports` (manager + admin). Пункт «Отчёты» в шапке у
других ролей **не показывается**, при попытке зайти по URL — `403`.

## 9. Уведомления

Файл — `app/core/notifications.py`. **Намеренно синхронные** (без Celery).
В DEBUG режиме письма летят в консоль (`EMAIL_BACKEND = console`).

4 события:
1. `notify_request_created` → клиенту при регистрации заявки
2. `notify_request_assigned` → исполнителю при назначении
3. `notify_status_changed` → клиенту при смене статуса (кроме `new`)
4. `notify_comment_added` → клиенту при появлении публичного комментария
   (внутренние с `is_internal=True` не отправляются)

Шаблоны — `app/templates/emails/<event>.txt` + `<event>.html`.

Вызов через `transaction.on_commit(...)` из сервисного слоя — чтобы не уйти
впустую при rollback. Сбои логируются, но не прерывают бизнес-операцию
(`fail_silently` через try/except в `_send`).
