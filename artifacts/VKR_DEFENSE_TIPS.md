## 2. Что обычно спрашивают на защите (и как отвечать)

### «Почему Django, а не React + FastAPI / Spring Boot / Node.js?»
> Django — зрелый full-stack-фреймворк с встроенной ORM, аутентификацией,
> admin-панелью и шаблонизатором. Для **прототипа ИС учёта заявок** это
> оптимальный выбор: один язык, один процесс, минимальная инфраструктура.
> Для данного масштаба (5 ролей, 14 моделей, <100 одновременных
> пользователей) микросервисная архитектура избыточна.

### «А что с нагрузкой? Сколько пользователей выдержит?»
> Текущая реализация — синхронный Django + PostgreSQL — уверенно держит
> **200–500 RPS** на одном процессе (django benchmark). При росте
> подключаем Gunicorn (4–8 workers) и nginx для статики. При тысячах
> пользователей — горизонтальное масштабирование (несколько инстансов за
> балансировщиком). Это **перспективы развития**, которые уместно упомянуть
> в заключении.

### «Чем ваш low-code-конструктор лучше, чем просто редактировать код?»
> Администратор **без навыков программирования** может через web-интерфейс
> (Django Admin) добавить произвольное поле в карточку заявки за 30 секунд.
> Не нужны: правки кода, миграции БД, деплой, перезапуск сервера.
> Это снижает стоимость владения системой и ускоряет адаптацию под
> новые бизнес-процессы.

### «Почему не Celery для уведомлений?»
> Для прототипа синхронная отправка email допустима: среднее время
> `send_mail()` через SMTP — 50–200 мс. При 10–20 заявках/день задержка
> незаметна. В production-окружении добавление Celery + Redis — **один
> из логичных шагов развития**, описанных в заключении.

### «Какие тесты есть? Процент покрытия?»
> 103 автотеста (pytest + pytest-django): модели, RBAC (5 ролей),
> машина состояний (6 статусов, 8 переходов), сервисный слой,
> email-уведомления, отчёты. Покрытие — **75–85%** бизнес-логики
> (модели + сервисы + permissions + reports). Не покрыты: views
> (интеграционный уровень) и шаблоны — это перспектива.

### «Зачем GIN-индекс? Почему JSONB, а не отдельные таблицы?»
> JSONB + GIN-индекс — способ хранить **произвольные** пользовательские
> поля без миграций. Альтернатива — EAV-модель (Entity-Attribute-Value),
> но она порождает десятки JOIN-ов. JSONB + GIN даёт одно поле на строку
> и при этом поддерживает быструю фильтрацию (`@>` оператор). Это
> промышленный паттерн, используемый в Jira, Notion, Salesforce.

### «А безопасность?»
> - RBAC на уровне view-функций (`permissions.py`): проверка роли на
>   каждом эндпоинте.
> - CSRF-защита Django (middleware).
> - Хеширование паролей (PBKDF2 по умолчанию).
> - Аудит-журнал всех значимых действий.
> - В production добавляется HTTPS (nginx/certbot) и CSP-заголовки.

## 3. Рекомендации по скриншотам

### Общие правила
- **Разрешение:** 1920×1080 или 1440×900 — не мельчить, но и не 4K
  (иначе текст слишком мелкий на слайде).
- **Формат:** PNG (без потерь).
- **Обрезка:** убрать панель задач Windows, лишние вкладки браузера.
  Оставить только адресную строку + контент.
- **Подсветка:** если хочешь обратить внимание на элемент — красная
  прямоугольная рамка (Snipping Tool → выделить), не стрелки.
- **Подпись:** в ВКР подпись «Рис. 3.XX — …» должна быть **ПОД**
  картинкой (ГОСТ).

## 4. Что писать в «Заключении» ВКР

Заключение — 1.5–2 страницы. Структура:

1. **Что было сделано** (перечислить 5–7 пунктов):
   - Спроектирована и реализована ИС учёта заявок...
   - Реализован low-code-конструктор пользовательских полей...
   - Реализована ролевая модель доступа (5 ролей)...
   - Реализована машина состояний заявок (6 статусов, FSM)...
   - Реализованы отчёты с визуализацией (Chart.js) и экспортом (CSV, XLSX)...
   - Реализованы email-уведомления...
   - Написаны автоматические тесты (103 кейса, pytest).

2. **Что подтверждает работоспособность:**
   - Все тесты зелёные;
   - Демо-данные подтверждают корректность бизнес-логики;
   - SLA-отчёт верно определяет просрочку.

3. **Направления развития** (2–4 пункта):
   - Подключение Celery для асинхронной отправки email;
   - REST API для мобильного клиента;
   - Интеграция с внешними каналами (Telegram-бот, email-to-ticket);
   - Расширение отчётов: прогнозирование нагрузки (ML).

## 5. Типичные ошибки на защите

| Ошибка | Как избежать |
|---|---|
| Читать слайды слово в слово | Рассказывай своими словами; слайд — подсказка |
| Слишком много текста на слайде | Максимум 5–7 строк; графика > текст |
| «Я не знаю» на вопрос | Лучше: «В текущей реализации это не предусмотрено, но в перспективе можно реализовать через...» |
| Паника при вопросе про нагрузку/безопасность | Заранее подготовить 1–2 предложения (см. выше) |
| Не уложиться в 10 минут | Репетируй 2–3 раза вслух с таймером |
| Живая демо не запустилась | Всегда имей скриншоты на слайдах как backup |
